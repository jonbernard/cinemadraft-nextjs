# Decisions

Locked during design on 2026-08-13. **Do not re-litigate these without the owner.**
Full rationale lives in `docs/superpowers/specs/2026-08-13-cinemadraft-nextjs-conversion-design.md`.

| # | Decision |
|---|---|
| D1 | Next.js 16 App Router, React 19 |
| D2 | Full TypeScript conversion (strict) |
| D3 | **MUI (latest stable)** as component substrate; new identity delivered through the theme layer. **Tailwind (latest stable) is the styling system for custom work** — MUI supplies components, Tailwind supplies bespoke styling (D29) |
| D4 | **Prisma (latest stable)**, with the driver adapter **selected by environment** (D32) |
| D5 | Neon Postgres via Vercel Marketplace (free tier) |
| D6 | ~~Upstash Redis~~ — **superseded by D23** |
| D7 | Clerk for auth, replacing Auth0 |
| D8 | Server Components + Server Actions; no general `/api` layer |
| D9 | Vercel Blob replaces Cloudinary |
| D10 | Data replicated exactly, **then identifiers normalized** (D27), then `prisma db pull` |
| D11 | Parallel run, then DNS swap |
| D12 | Contract tests at the repository layer + Playwright E2E |
| D13 | Realtime ships after cutover; polling until then |
| D14 | New features ship after cutover |
| D15 | Light and dark themes both first-class; dark is default |
| D16 | All prior committed work in this repo is ignored — started fresh |
| D17 | Port priority: auth, dashboard, draft — then everything else |
| D18 | A **parity audit** (phase 7) follows the priority trio and gates cutover; output is `docs/PARITY.md` |
| D19 | Scoring becomes a **pure, unit-tested rule** with materialized results and bounded event-driven recompute |
| D20 | Search is **local-first**, merged with cached TMDB, and context-aware (draft / browse / award admin) |
| D21 | The **award show page gets its own phase** — it is the input to the entire scoring pipeline |
| D22 | **Active season year is data, not config** — `AvailableYear.isActive`, settable from the running app; `NEXT_PUBLIC_ACTIVE_YEAR` is deleted |
| D23 | **Vercel Runtime Cache** replaces Upstash for caching; **realtime transport deferred to phase 14** |
| D25 | **No bulk user migration** — accounts are claimed on first Clerk auth with a **verified** matching email. Linking on an unverified email is an account-takeover vector |
| D27 | **snake_case normalization** — plural snake_case tables/columns/enums, drop NULL `password`+`salt` and `SequelizeMeta`. **No PK type changes.** Script is committed and repeatable, because cutover re-dumps from Heroku's original schema |
| D26 | **Passwordless.** Clerk offers email verification code + Google only; password is disabled. Every sign-in is email-verified by construction, and no user ever migrates or resets a password |
| D24 | **Blob uploads are `access: 'public'`.** Content is avatars, already public via Cloudinary and shown to other league members by design |

| D28 | **Always latest stable.** Every dependency is pinned to the newest stable release at the time it is introduced — never a pre-release, never an older major for familiarity. Verify against the npm registry rather than assuming a version from memory |

| D29 | **MUI and Tailwind coexist via CSS cascade layers.** `AppRouterCacheProvider` runs with `enableCssLayer: true`, and the layer order is declared `@layer theme, base, mui, components, utilities`. `mui` sits above `base` so Tailwind preflight cannot strip MUI component styling, and below `utilities` so Tailwind classes win without `!important` or specificity hacks. Design tokens (§6) are defined once as CSS custom properties and consumed by both |

| D30 | **TypeScript stays on 5.x until after cutover** — an explicit exception to D28. TypeScript 7 is a ground-up native rewrite, and Next 16, Biome and Prisma all declare support against 5.x (Prisma's peer range is `>=5.4.0`). Adopting it during the data layer would mean debugging toolchain gaps alongside a Prisma major. `^5` cannot resolve to 7, so the pin is already safe. Revisit as its own task post-cutover |
| D31 | **Prisma 7 config lives in `prisma.config.ts`, not the schema.** `datasource.url` is a hard error in 7 (P1012), env vars are no longer auto-loaded, a driver adapter is mandatory, and the generator is `prisma-client` with a required `output`. Generated client goes to `generated/prisma` — gitignored, regenerated at build, and deliberately not under `app/` where Next's route scan would reach it |

| D32 | **Two driver adapters, chosen at runtime.** `@prisma/adapter-neon` for Neon (Preview/Production) and `@prisma/adapter-pg` for the local Docker database (development and tests). This is not a preference: `@neondatabase/serverless` speaks Neon's WebSocket/HTTP protocol, not the Postgres wire protocol, so it cannot connect to local Postgres at all. Verified — the same query fails inside `@neondatabase/serverless` and passes through `@prisma/adapter-pg` |

| D33 | **Repository DTOs are derived from the generated Prisma models, not retyped by hand.** `export type Movie = Pick<MovieModel, 'id' \| 'title' \| …>`, with `Omit` plus a restated field wherever a column is normalized (bigint → number, Decimal → number). The field *list* stays explicit, so a new column cannot silently widen what components receive; the field *types* come from the schema, so they cannot drift from it. Enums are imported from `generated/prisma/enums` and re-exported by the owning repository rather than hand-written as string-literal unions. **Every such import is `import type`** — TypeScript erases it, so no Prisma runtime crosses the boundary; a value import would pull the client into whatever bundle imports it. `app/`, `actions/` and `components/` may not reference `generated/prisma` at all, even for types: they consume repository DTOs. The `layering` CI job enforces all three rules |

| D34 | **Roster size is not a stored value.** The number of movies a seat drafts changes every year and every league decides its own — so the app does not persist it, does not configure it, and does not validate against it. A roster is whatever `draft_picks` holds for that seat and season: 6, 8, 30. The production data already varies (7, 8 and 9 across seasons) with no constraint enforcing any of it. Every consumer — roster strip, scoring, draft board, standings — derives length from the rows it was given. Nothing may hardcode a cap, and nothing may read a roster-size setting, because there is none to read |

| D35 | **Tokens are declared in TypeScript and mirrored into CSS, with a test holding the copies together.** Tailwind 4 reads its theme from CSS and MUI reads its from JS, so one source cannot feed both — the duplication is structural, not laziness. `theme/tokens.ts` is authoritative; `app/globals.css` mirrors it; `theme/tokens.test.ts` parses the CSS and asserts they agree, verified by mutation to fail on a single changed hex digit. Rejected alternatives: generating the CSS from TS at build time (a build step and a generated file in the repo, to avoid a test that already catches every drift), and letting MUI's `--mui-palette-*` variables be the only tokens (names the design system after the component library, and Tailwind utilities would read MUI's shape rather than the design's) |
| D36 | **One attribute drives both styling systems.** MUI's `colorSchemeSelector` is set to `data-mui-color-scheme` and Tailwind's `dark:` variant is bound to that same attribute, so a single toggle switches both and no component reads a theme hook to decide what to render — which is what D15's "no component branches on theme" requires in practice. Dark-by-default needs `defaultMode="dark"` on **both** `ThemeProvider` and `InitColorSchemeScript`: `defaultColorScheme` only names the CSS fallback palette, while the *mode* defaults to `system` |
| D37 | **Colour lives only in `theme/`.** A hex literal under `components/` or `app/` is a colour outside the system: it cannot be themed, it does not swap, and no contrast test covers it. The `layering` CI job fails on one. When a component needs a colour that does not exist, the fix is to add it to `tokens.ts`, mirror it into `globals.css`, and add its pair to `contrast.test.ts` — never to inline it |

| D38 | **One claim path, two entry points.** `syncClerkIdentity` is the only code that may attach a Clerk identity to a `User`. The webhook calls it and so does `getCurrentUser`, because a webhook is asynchronous and independently retried — a member can finish signing in and reach a page before it lands, and a delivery can be dropped. Locally and in Preview it never arrives at all, since Clerk posts to the deployed host. Sharing one function means the two security rules cannot hold on one path and be forgotten on the other |
| D39 | **Auth pages live at `/auth/sign-in` and `/auth/sign-up`** — a real path segment, not a route group. The proxy's public matcher is `/auth/(.*)`, and `NEXT_PUBLIC_CLERK_SIGN_IN_URL` points there so a protected route redirects to the app's own page rather than Clerk's hosted `accounts.dev` screen. The first thing a returning member sees is the app's identity and the "your leagues come with you" copy, not a stranger's domain |
| D40 | **The proxy enumerates public routes, never protected ones.** A page added under `(app)` is protected by default, and forgetting to list it fails closed. The reverse leaks a page the first time someone forgets — and silently, because the page renders perfectly well to a stranger |

| D41 | **The pure scoring rule ships in Phase 5, not Phase 9.** Standings are the dashboard's whole point and cannot be computed without it, and deferring would mean writing a throwaway calculation now and a real one later — two definitions of the rule, differing quietly. `lib/services/scoring.ts` is pure and synchronous with no I/O; Phase 9 keeps its actual scope (materialized results, bounded event-driven recompute) and calls this same function, so the materialized copy cannot drift from what the tests pin. Consistent with D19, which asks for a pure unit-tested rule *and* materialization — this splits the two across the phases that need them |

| D43 | **No Clerk credentials in GitHub; E2E is a local gate.** The owner declined to store Clerk keys as repository secrets, and the app cannot render without them — `ClerkProvider` requires a publishable key and the proxy requires a secret key — so Playwright cannot run in CI at all. The steps are **skipped visibly** rather than allowed to self-skip on absent keys, because a suite that quietly skips reports green while proving nothing. `npm run test:e2e` moves onto the pre-cutover checklist (Phase 12) and must be run locally before any release; this covers the auth flow *and* the Phase 1 cascade-layer smoke assertions. CI still runs 233 unit tests against a real Postgres, including every security test |

| D44 | **Public by default; private only where the page is about *you* or acts for you.** Confirmed against the source app's own guards (`src/routes/index.js`), which already worked this way — so this is parity, not a new idea. **Public:** the dashboard `/`, browse, award shows, live pages, movie detail, rules & scoring, join-by-uuid, **and league pages** (they were never guarded). **Private:** my-leagues, league create, draft list, watchlist, reviews, user profile, settings, and anything admin. A page with a public variant renders for a null user and simply omits the parts that are about a person — it must never fall back to *somebody else's* data. Two rules follow: (a) every public page must render with `getCurrentUser()` returning null, and (b) a public page may not include user-scoped data even when a session happens to exist and the query would succeed |
| D45 | **The proxy keeps enumerating public routes, even though most routes are public.** With the list inverted the failure modes are asymmetric: forgetting to list a public page makes it *protected*, which is visible and harmless, whereas enumerating protected routes means forgetting one *exposes* it, silently and to everyone. The list grows deliberately, and each addition is an explicit "this is safe to expose" judgement. Pages additionally call `requireUser()` for themselves, so the guarantee does not rest on the matcher alone |

| D46 | **The owner enters every pick, by design — confirmed by the owner 2026-08-15.** The draft happens on a video call: the owner keeps the selection on the right player, that player says their pick aloud, and the owner searches for the film and assigns it to their seat. This is the intended workflow, not a limitation of the old app — so there is no clock, no turn timer and no on-the-clock cell, and the schema has no column that could hold one. Spec §6.7's "cell on the clock" describes a mechanism this product deliberately does not have. **What the UI must optimise for instead is the call itself:** the owner needs to see whose turn it is in the running order, search fast, and assign in as few actions as possible, because twelve people are waiting on every pick. A self-service timed draft is recorded as a *possible future enhancement*, not a planned phase — see `docs/PLAN.md` phase 15. |
| D47 | **League ownership is checked against the parsed `ownerIds`, never the raw column.** The source authorizes every pick, reorder and deletion with `league.owner.includes(req.user.id)`, and `leagues.owner` is TEXT holding a JSON array — league 1's value is the literal string `[3]`. That is a substring match, not a membership test: `"[31]".includes(3)` is **true**, so a stranger passes the ownership check on someone else's league, while `"[13]".includes(3)` is false, locking the real owner out. `lib/services/league-access.ts` is the single place this is decided, and it fails closed on an empty list or a signed-out caller |

| D48 | **The draft board is a realtime consumer, alongside the live award-show page.** The owner enters picks on a video call (D46) while the league watches the board, so a pick that only appears on refresh means a dozen people refreshing in unison. Confirmed by the owner 2026-08-15: live updating matters and is tackled **with the live awards page**, not before — the two share one transport, chosen in phase 14 (D13, D23). Until then the board is server-rendered per request and a pick is visible on navigation. **What this constrains now:** the board and its cells take their data as plain props from `lib/services/draft.ts` and hold no state of their own, so realtime is added by changing who supplies the props — a subscription wrapper — rather than by restructuring the components |

| D49 | **Mobile-friendly by default; owner-only tools are desktop-first.** Confirmed by the owner 2026-08-15: most members use the site on a phone, so every member-facing page is designed for a phone and scales up. The exception is tooling only the owner uses — chiefly the draft console — which is desktop-first, because it is operated once a year on a video call from a laptop while searching and typing. **This is a design instruction, not a breakpoint rule:** a wide table that technically scrolls sideways on a phone is not mobile-friendly. Where a desktop layout's value *is* its width — the draft board's aligned round columns, which exist so seats can be compared — the phone gets a different presentation of the same data rather than a squeezed copy. Both come from the same props, so there is no second source of truth |

| D50 | **A film may be taken once per group, not once per league — and the draft order is a snake.** Both are measured against the restored data rather than assumed. Uniqueness: across all 1025 production picks no film is ever repeated *within a group*, while films are routinely taken by several groups of the same league in the same year — 25 films in league 1's 2017 season were each taken five times. Each group is its own independent draft, so a league-wide rule would refuse writes the league has always made. Order: reconstructing every pick sequence from `draft_picks.created_at`, the three seasons drafted under the current live-call workflow match a snake almost exactly (2024 84/84, 2025 108/108, 2026 116/117), while 2017–2022 do not and their timestamps arrive in clumps that do not describe a live draft at all. The single 2026 exception is a pick taken out of sequence — the "someone missed their turn" case the owner described — so the suggested seat is derived as *the seats behind this round, in snake order* and is always overridable. `addPick` enforces the group scope; `lib/services/draft-order.ts` derives the turn |

| D51 | **Server Actions return an `ActionResult` union; they do not throw at the client.** An exception thrown out of a Server Action reaches the browser as an opaque digest — React deliberately replaces the message in production — so "you do not own this league", "that film is already taken" and a crash all arrive looking identical. The first two are ordinary outcomes the owner reads mid-draft. `actions/result.ts` converts the app's own `AppError` codes into failures and **re-throws everything else**, so a connection failure or a programming error still reaches the error boundary and the logs rather than being reported to the league as a refused pick |

| D52 | **Writes are authorized against facts derived from the row, never from the request.** The source route read `leagueId` and `draftId` from the same untrusted body, checked ownership against the first and wrote to the second, and never checked they agreed — sending your own league's id alongside someone else's seat passes the check on a league you own while the write lands on a league you do not. `actions/draft/guard.ts` loads the seat, takes its league from that, and authorizes there; removal and reordering derive the seat from the stored pick for the same reason. Related: reordering is expressed as an ordered list of pick ids rather than `{id, order}` pairs, so duplicate or missing rounds are not representable, and it is checked to be a permutation of the seat's own picks before a single transaction writes 1..N |

| D53 | **Parity is measured in capabilities, not endpoints, and a row is ported / deficient / dropped with no fourth option.** D8 removed the HTTP layer, so an endpoint-for-endpoint audit would have marked the entire application deficient while being true of nothing — several endpoints plus a page routinely make one capability. "Partial" is banned as a verdict for the same reason a half-green test is: the matrix exists so that a green row can be read as "yes, a person can do that", and anything that half works is therefore deficient. Every row cites evidence on both sides — a source `file:line` and, when ported, the file in this repo that delivers it — because a matrix of remembered verdicts would be believed without being true. `docs/PARITY.md` |

| D54 | **The source app is never modified, including to fix live security bugs.** Confirmed by the owner 2026-08-15, when the audit found six unauthenticated write endpoints on production — `POST`/`DELETE` on nominations and winners, `POST /movie`, `POST /years` — which are the *scoring inputs*, so anyone on the internet can alter every league's standings. The remedy is that the port ships those writes admin-gated (P10.T28/T29) and cutover closes the exposure; the old tree stays a read-only reference whatever is found in it. The same rule governed D47, and it is why every finding in this audit is a matrix row rather than a patch |

| D55 | **Source bugs are recorded as bugs, not reproduced as behaviour.** The audit found ten, each read in the source and, where the data could settle it, measured: `Winners.movie` joins `Movies.id = Winners.id` instead of on `movieId`, so **733 of 734 winner rows resolve to the wrong film**; league ownership is a substring match (D47, 29 wrongly-admitted pairs); `verifyLeagueOwner` is a no-op on the route that adds a seat; `DELETE /draft/:id` has authentication but no authorization; `PUT /league/:id/status` writes the whole body and inserts a duplicate seat on every call; a hardcoded `year: 2024`; reorder writes that are never awaited; and two `:type` segments that are parsed and then ignored. `PARITY.md` lists them with evidence so that nobody closes a Phase 10 row by faithfully reimplementing one — the risk is real, because "match the old behaviour" is exactly the instruction a parity phase gives |

| D56 | **TMDB is the film catalogue and `movies` is a cache of it, so a `TMDB_API_KEY` is required rather than optional.** Corrected by the owner 2026-08-15, mid-phase: a film enters the local table the first time somebody drafts or nominates it — which is why all 1,355 restored rows carry a `tmdbId` — so a search that consults only the cache can only ever return films the league has already used. That is the opposite of what search is for during nominations season. Two consequences: **search always asks TMDB**, never gated on how many local results turned up (a query like "wicked" matches several cached films and would otherwise never reach the new release somebody is trying to draft); and **both write paths ingest an uncached film** through `lib/services/film-ingest.ts`, ported from the source's `saveFilm`, because every id the rest of the app deals in is a local `movies.id`. The rate limit is handled by caching identical queries, not by declining to ask. Without a key the app degrades to searching its own history — existing pages render, existing films are findable, and nothing new can be drafted or nominated — which is a broken install, not a mode |

| D58 | **A film belongs to an award season if it was released up to five years before it, weighted by how likely that gap is.** Confirmed by the owner 2026-08-15 as their own search practice, and the restored data explains why: across every nomination with a known release date, **96.5% sit exactly one year before their season**, 1.5% in the season year, 1.9% two years before, and a real tail beyond that. The tail is **shorts and foreign-language films**, whose TMDB primary release year is a festival or home-country date years before the award recognising them — *This Is Endometriosis* is a 2022 film nominated for Best Short Film in 2026; *The Alan Dimension* is a 2016 short nominated for Best Short Animation in 2017; *Son of Saul* and *The Handmaiden* carry 2015 and 2016 dates against 2017 and 2018 seasons. The window is therefore **graded, not flat**: full weight at one year before, less at zero and two, less again out to five. A flat ±5 would rank a 2021 film level with a 2025 one for the 2026 season and discard the signal that is right 96.5% of the time. Nothing is excluded either way — this is a ranking boost, so a film outside the window (a 2004 title RAZZIE-nominated in 2025) is still findable |
| D57 | **The award year is never sent to TMDB as a release filter, because a season honours the previous year's films.** Measured in the restored data: of the 526 nominations in the 2026 season, **507 are 2025 releases and 7 are 2026 releases** — the same shape in 2025 (503 of 520 are 2024 films). An early implementation passed the season as `primary_release_year`, which reads as sensible scoping and in fact hid 96% of the candidates, so an admin entering nominations would have searched and found nothing. The season is applied in `search-ranking.ts` instead, where being in season is a **boost covering the award year and the year before it**, and nothing is excluded for being a year out. Found by the E2E test that nominates a real film TMDB knows and the app has never cached — a unit test with a stubbed remote could not have caught it, because the stub did not care what it was asked |

| D59 | **Scores are computed on read, never materialized.** `PLAN.md` and spec §11 specified three derived tables — `MovieScore`, `TeamScore`, `LeagueStanding` — with bounded recompute, a full-recompute command, a reconciliation job and a nightly cron. Cancelled by the owner 2026-08-16 after measurement: a full 16-seat league board costs **8 ms** including scoring, every film nominated in a season costs 7 ms, and all 1,355 films at once cost 16 ms. The spec's premise was that "cost scales with league size on every page view", and at 13 leagues and 60 people it does not scale to anything. Materializing would buy ~8 ms and introduce **drift** — a second copy of the truth that can silently disagree with it — and every mitigation the spec proposed (reconciliation, cron, bounded recompute) exists solely to manage a risk that not materializing does not have. Standings that are quietly wrong are a much worse failure for this app than a page that takes 8 ms longer. Revisit only if measurement, not intuition, says load demands it |

| D60 | **`nominations.year` is an integer, fixed at the column rather than at each call site.** It was the only year column in the schema that was TEXT, and the inconsistency was not cosmetic: comparing it against a number matches *nothing*, so the failure mode is a film silently scoring zero rather than an error. It caused wrong answers three times during the port — in `scoring.ts`, in `award-show.ts`, and finally in a fixture whose `year` was captured as `"2017"`, which made a ledger test return no rows. Ten call sites were each carrying a `String()` or `Number()` conversion to work around it, which is a workaround repeated ten times, not a fix. Migrated 2026-08-16 after verifying the restored data was clean — 4,559 rows, zero nulls, zero non-numeric values, range 2017–2026 — so the cast is lossless. The go-live path was rehearsed end to end on a scratch database: restore the dump (which recreates the column as TEXT), `migrate resolve --applied 0_init`, `migrate deploy`, and the column arrives as an integer with its data intact. **The source app is untouched and still stores TEXT** (D54) |

| D61 | **The vocabulary is log in / log out / register — never sign in, sign up or sign out.** Set by the owner 2026-08-16. Applied to routes (`/auth/login`, `/auth/register`), page headings, the nav control, and **Clerk's own component strings**, which say "Sign in" and "Sign out" out of the box and are overridden through the `localization` prop in `app/providers.tsx`. Clerk's component *names* stay as they are — `SignIn`, `SignUp`, `UserButton` — because those are its API, not our vocabulary. Registration is "register" rather than "sign up" for consistency: mixing *sign* and *log* across three adjacent actions is the kind of seam that makes an interface feel assembled from parts, and "an action keeps the same name through the whole flow". Verified in a browser rather than by grep — the rendered pages contain no occurrence of "sign in" or "sign up" |

| D62 | **The navigation carries the source app's seven destinations, not spec §6.9's four.** §6.9 proposed consolidating Browse, Watchlist and Draft List into a single Films destination and moving Rules & Scoring into the ledger; the owner overrode it 2026-08-16 — the league knows the app by these seven names. The consequence is a **drawer on phones rather than a bottom bar**: a bottom bar carries five items before targets fall under the 44px minimum, so seven would mean shrinking the targets or hiding items behind a "More" sheet. The drawer is also what the source used (`src/layouts/dashboard/navbar`), so it is the pattern members already know. It is a native `<dialog>` opened with `showModal()`, which supplies the focus trap, `Escape`, the inert background and the backdrop — four things that are easy to write badly, and all verified in a browser rather than jsdom, which implements none of them. Entries appear as their pages are built (`ready: false` marks one Phase 10 still owes), so the nav never links to a 404 |

| D63 | **The public film page never writes.** `/films/[tmdbId]` is keyed by a TMDB id and is public (D44), so it renders for films the app has never ingested — which is the case the source screenshots show. The straight port would write on that read: `server/routes/movie/movie.js:38` calls `Movies.update` to refresh posters on every GET, and reaching for `ensureFilm` would create a row per unknown id. On a public route that is unbounded insert traffic from crawlers against a free-tier database, and it would fill `movies` with films nobody drafted — breaking the invariant the rest of the port relies on, that **a row in `movies` means somebody used that film** (D56). So the page reads the local row if one exists (for scoring) and otherwise renders entirely from TMDB. `ensureFilm` still runs where a person deliberately acts: drafting, nominating, and marking a film watched |

| D64 | **A "watchlist" in this app is a list of films you have watched, not films you intend to watch.** Read out of the source rather than assumed from the table name: `WatchButton` is titled "Mark as watched" / "Watched!", its toast reads "Marked as watched", and the action it offers next is "Write a review" (`src/components/WatchButton.js`) — reviews hang off the same rows. The green `+` badge on a browse poster is therefore an *I have seen this* mark and flips to a check. The route stays `/watchlist` because that is the URL the league has, and `PARITY.md` already names the capability "Your watched films"; every piece of visible copy says **watched**, and none says "add to watchlist". Getting this backwards would have shipped a feature that reads as the opposite of what it does |

| D65 | **Browse pages through the URL instead of infinite-scrolling.** The source used `useInView` to append pages into component state (`src/pages/browse/index.js`), which cost four things: a film could not be linked, the back button lost the reader's place, page 12 was unreachable from a keyboard, and the sentinel fired again on every re-render. Browse is now `?when=past|future&page=N` with a "Load more" that is a real link to the next page, so it works before hydration, is crawlable, and is shareable. Recorded in `PARITY.md` as a deliberate betterment rather than a parity row. The same reasoning moved the past/future control out of `useState` and into the URL |

| D66 | **A test targets an element by `data-testid`, and production strips the attribute.** Set by the owner 2026-08-17, immediately after a name-based locator cost real time on a bug that did not exist: `e2e/browse.spec.ts` found the watched badge with `getByRole('button', { name: /Mark .* as watched/ })`, and marking a film **changes that name by design** so a screen reader hears the new state — so after the click the locator silently resolved to the *next* film's badge and reported `aria-pressed=false`. The feature was correct (the row was written and a reload showed it) and the test was lying, which is the worst kind of failure because it looks exactly like a real defect. The rule is therefore: the **handle** is a testid and stable; the **assertion** stays on roles and accessible names, because those are what a reader actually gets. Stripped from production by `compiler.reactRemoveProperties` in `next.config.ts` — a test hook is dead weight in every payload and an invitation to depend on it from outside the suite — with `KEEP_TEST_IDS=1` set by Playwright's `webServer` command, which is required rather than optional because the E2E suite deliberately runs against a production build. Verified both ways: 0 occurrences in a normal build's JavaScript, 4 with the flag |

| D67 | **The visual direction is Screening Room: a floating rail, a slim strip and a content panel on a hue-shifted dark ground.** Chosen by the owner 2026-08-17 from three directions rendered side by side against the real league board. It replaces the desktop top bar, which the owner named as one of three complaints. Measured against ten live products the same day: Spotify's desktop shell is a `#121212` rail at 8px radius floating on black, and that framing is why a dense list UI reads as a media player rather than an admin console. It also scales past seven destinations where a horizontal bar does not. **Supersedes §6.9's layout** (the *count* was already overridden by D62). Full rationale: `docs/superpowers/specs/2026-08-17-design-system-and-storybook-design.md` 🔴 **The rail is 208px, and it collapses at `xl` (1280px), not `lg`.** Task 18 measured it in a browser at 1280px against a league board carrying 10 seats and 10 rounds: at the spec's 236px the board container was 902px with poster cells 62.7–80.1px (mean 70.8); at 208px it is 930px with cells 66–81.1px (mean 73.0). The ~110px poster floor in §11.4's decision rule is what fired, and the rail's own labels were verified not to overflow or wrap at the narrower width. Two things matter more than the 28px. **§11.4's own arithmetic is wrong** — it predicts ~128px per poster on a 7-round board where the measured figure is 96.1px, because its sum ignores the board's ~114px seat column and the page's own padding; anyone re-deriving the width cost from §11.4 will be ~25% too optimistic. And **the 28px is not what makes that board legible** — the desktop `DraftBoard` table compresses rather than scrolling, which is an open question rather than a decision (see **Still open**). |

| D68 | **The dark ground is violet-warm, not neutral — `#0A0910`, not `#0B0D10`.** The single highest-leverage change in the redesign, and the one that addresses "too techy/nerdy" most directly. Measured evidence: Sleeper's ground is `#05091D`, a navy at essentially the same *luminance* as a neutral near-black, and the hue shift alone stops a dense stats UI reading as a terminal. Neutral or cool-blue near-blacks (`#0D1117`, `#121212`, `#14181C`) are the developer-tool signature; warm and violet-shifted darks read as cinema. Applies to light too: `#EFEAE2` warm paper |

| D73 | **The radius scale is 3 / 6 / 10 / 16 / pill, and posters use a proportional `clamp()` instead of a token.** Buttons are 6px — never 0 (which reads unstyled and was complaint #2), never a pill (which reads as a game; Underdog's 20–40px family is why its stats tables stop looking like tables). ## Explicitly rejected

- **Supabase** for database or realtime — rejected by the owner.
- **Gold-on-black palette** — the default for awards products; would be indistinguishable from any Oscars microsite. 🔴 D69's **brass is not this**: a desaturated metallic used as text, eyebrows and a small seal against a violet-warm ground, never a gold fill on pure black.
- **Turborepo, npm workspaces and Vercel microfrontends** — see D76. Microfrontends are free-tier accessible (2 projects, 50K routing requests) but exist to serve many projects under *one domain with path routing*; Storybook wants its own URL.
- **Fraunces as the display face** — full weight range and no fallback rule needed, but the owner chose Instrument Serif 2026-08-17. D70's semantic rule makes the weight range unnecessary.
- **Instrument Sans replacing Archivo** — measured and rejected; see D71.
- **`@storybook/addon-vitest`** — a third overlapping test layer on top of Testing Library and Playwright, requiring browser-mode Vitest and Playwright binaries in CI. Revisit only to pair it with `addon-a11y` for axe assertions on every story, which would be a genuinely new capability. Story reuse without it is `composeStories` in the existing jsdom setup.
- **`@storybook/addon-themes`** — its `withThemeByDataAttribute` writes `data-mui-color-scheme` directly, but **MUI owns that attribute**; the result is two sources of truth, a stale `useColorScheme()`, an unwritten `mui-mode` key, and MUI overwriting the attribute on mount. Drive MUI's own `setMode()` from a toolbar global instead.
- **`storybook-design-token`** — parses annotation comments out of stylesheets, a model that fits Sass and CSS-variable files rather than Tailwind 4's `@theme` block. A hand-written MDX page that reads the live custom properties cannot drift.
- **The 2026 AI-default look** — `#0A0A0A`/`#171717` plus one violet or cyan accent plus Inter plus 8px radius (the shadcn-with-default-tokens appearance); glassmorphism; bento grids; aurora gradient hero blobs; expanded-caps display faces; neon glow accents; 16–24px radius on table rows and inputs; monospace as a data affectation across labels; dark-mode-only with no light theme. Named explicitly so none is reached for later.
- **Reusing the prior scaffold's `schema.prisma`** — valuable, but D16 overrides.
- **Keeping Auth0 as a Clerk OAuth connection** — no migration risk, but retains the vendor being removed.
- **Bulk-importing users from Auth0 into Clerk** — superseded by D25. Auth0 does not export password hashes without a support request, and all 51 users are email+password. Claiming needs only the webhook that already existed.
- **Running `prisma init`** — it writes `.claude/skills/`, `.windsurf/skills/`, `.agents/skills/` and `skills-lock.json` into the repo root uninvited. `schema.prisma` and `prisma.config.ts` are written by hand instead.
- **`previewFeatures = ["driverAdapters"]`** — GA since Prisma 6.16; declaring it now emits a deprecation warning.
- **Using `@prisma/adapter-neon` everywhere, including locally** — it cannot reach a plain Postgres server. The alternative, running a WebSocket proxy in front of local Postgres, adds a moving part to every developer machine and every CI run to avoid one conditional in `lib/db.ts`.
- **Rewriting UI to shadcn/Tailwind** — D3 keeps MUI for components. Tailwind is added for custom styling only (D29), not as a component library.
- **Excluding Tailwind entirely** — the original reading of D3. Reversed by the owner: MUI for components, Tailwind for everything bespoke.
- **`!important` or specificity overrides to make Tailwind beat MUI** — cascade layers solve this properly; escalating specificity does not compose.
- **Building on MUI 7 / Prisma 6** — the versions originally written into the spec. Both were taken from memory rather than the registry and were stale: MUI shipped 9.x and Prisma 7.x. Superseded by D28.
- **Unifying primary key types** — `Users.id` is an int, `Awards.id` a UUID. Unifying rewrites every PK and FK for no user-visible benefit.
- **Transforming the dump file before restore** — restore as-is then rename in SQL; catalog renames cannot mismap data, dump rewrites can.
- **Upstash Redis via the Vercel Marketplace** — no longer has a free tier; smallest plan is pay-as-you-go and requires a credit card, which violates the free-only constraint.
- **Vercel Edge Config for the active year** — right tool for middleware-latency flags, wrong tool for domain data that belongs beside the years table.
- **Consolidating navigation to four destinations (§6.9)** — built that way first, then reversed by the owner. The spec's reasoning holds in the abstract, and it loses to the fact that sixty people already navigate by the seven existing names. Superseded by D62.
- **A phone bottom bar** — correct for four destinations and wrong for seven: the targets would drop below 44px or two items would hide behind a "More" sheet. Superseded by D62.
- **"Log in" beside "Sign up"** — the most common pairing in modern products, and it puts two vocabularies in one flow. The register page is the single most important copy in the migration (D25), so its heading matters more than convention. Superseded by D61.
- **Converting `nominations.year` at each call site** — how the port worked until 2026-08-16, with a `String()` or `Number()` at ten places. Every one of them was correct; the bug was the eleventh, which is why the column changed instead. Superseded by D60.
- **Materialized `MovieScore` / `TeamScore` / `LeagueStanding` tables** — spec §11's design, planned in detail and dropped before a line was written. It solves a performance problem that measurement could not find (8 ms per league board) at the cost of a correctness problem that would be real. Superseded by D59.
- **A nightly reconciliation cron** — the spec's own guard against materialization drift. With nothing materialized there is nothing to reconcile; the *useful* version of that idea is verifying the port against the captured production fixtures, which Phase 9 does once in CI rather than nightly forever.
- **A flat ±5-year season window** — the obvious reading of the owner's "+/- ~5 years". It treats a film released one year before the season, which is 96.5% of all nominations, as no more likely than one released five years before, which is a handful of shorts. The window is the owner's; the weighting comes from the data. Superseded by D58.
- **Scoping the TMDB request by the award year** — §10 says the search is "year-scoped" for the award-admin context, and applying that to the remote *request* rather than to ranking hid almost every film being nominated. Superseded by D57.
- **Treating TMDB as an optional enhancement behind an interface** — how the phase was planned and built, on the reading that 1,355 local films made search complete on their own. They do not: they are a cache of films already used, so the design answered every question except the one search is for. Corrected by the owner. Superseded by D56.
- **Calling TMDB only when local results are thin** — §10's own words ("call TMDB only when local results are thin"), implemented as a threshold of 5. It saves requests by hiding new releases behind common words, which is the failure it was meant to prevent. Superseded by D56.
- **Auditing parity endpoint-by-endpoint** — the obvious reading of "enumerate all 18 route files", and it measures the wrong thing: the port deliberately has no HTTP layer, so a faithful endpoint audit reports 0% parity for an app that had already ported auth, the dashboard and the whole draft. Superseded by D53.
- **Allowing a "partial" verdict** — it was tempting for rows like league standings, which exist on the dashboard but not on the league page. A partial row cannot gate a cutover, because nobody can act on "mostly". Those rows are deficient and carry a task.
- **Fixing the six unauthenticated writes on Heroku** — a four-line diff matching what `awards.js` and `events.js` already do, on a live hole in the scoring data. The owner's rule that the source tree is never touched stands regardless (D54); the fix ships in the port instead.
- **Trusting the source app's `{id, order}` reorder payload** — it lets a client send duplicate or missing positions, and the route applied them in an async `forEach` that awaited none of them, so a half-applied reorder left two picks sharing a round. Superseded by D52.
- **League-wide uniqueness for a drafted film** — the intuitive rule, and it contradicts the data: films are taken by several groups of the same league every year. The scope is the group (D50).
- **A turn order counted from the number of picks made** — it breaks the moment someone misses a turn, which the 2026 data shows happening. Deriving the turn from which seats are behind handles the skipped seat with no special case.
- **Porting the source app's ownership check as written** — `league.owner.includes(user.id)` against an unparsed JSON string. It is not a near-miss; it admits the wrong user and rejects the right one. Superseded by D47.
- **Making league pages private** — I had assumed membership and real names implied privacy, and started building that way. The source app's routes show league pages were never guarded, so gating them would be a parity regression, not a hardening. Checked rather than assumed. Superseded by D44.
- **Putting the Clerk publishable key in CI as a non-secret** — it is public by design (it ships in the browser bundle), so it would not be a leak, and it would restore the `smoke.spec.ts` cascade-layer coverage. Not done because the proxy still needs the *secret* key for any page behind auth, so it would buy back only the marketing pages while putting Clerk configuration in the repo against the owner's stated preference. Available if that trade ever looks worth it.
- **Mocking Clerk's `verifyWebhook` in the webhook tests** — it would assert the endpoint's only authentication control against a stub that always agrees. The tests compute real svix signatures instead, and the positive case proves the signing helper is right, so the four rejection cases are genuine rather than everything failing uniformly.
- **Relying on the Clerk dashboard's account-linking setting to prevent double identities** — it should prevent them, but the claim guard must not depend on a switch staying on. The guard refuses and logs instead; linking is defence in front of it, not the defence itself.
- **Clipping each RGB channel independently to bring a poster accent into gamut** — the obvious implementation, and it moves hue by an arbitrary amount, which defeats the entire purpose of deriving the colour from the poster. Out-of-gamut colours are fitted by bisecting chroma at fixed lightness and hue instead, holding worst-case hue drift to 2.1° across an exhaustive lattice.
- **Searching for a readable accent lightness with a bounded loop and a fallback colour** — a loop that can exhaust returns a silently wrong colour. The walk instead runs to the true limit, where gamut fitting has driven chroma to zero and the result is white or black at ~19:1, so the 4.5:1 floor holds by construction and the test sweep confirms rather than establishes it.
- **A `Movie.accentHex` passed straight to a component** — a black-and-white poster yields near-black, which on the dark ground is invisible and, as a contribution bar, reads as "scored nothing". Raw accents always pass through `clampAccent` first.
- **Storing roster size** — as a column on `available_years`, as a per-league-per-year setting, or as a yearly constant. All three were on the table; the owner rejected the premise. The app does not need to know the number, so any place it stored one would be a second source of truth that could disagree with `draft_picks`. Superseded by D34.
- **Greying out zero-point films in the roster** — the strip is ordered by draft position, not performance. A last pick may be the best pick.
- **Hand-writing repository DTO fields to keep the boundary "real"** — the original reading, applied to `movies.ts`. Reversed by the owner: it duplicates every column's type and guarantees drift the moment the schema moves. `Pick` from the generated model keeps the explicit field list that made the boundary real, without the duplication. Superseded by D33.
- **Deriving DTOs with `Prisma.<Model>GetPayload<{ select: typeof SELECT }>`** — tighter coupling to the query than to the schema, and it forces the DTO to change shape whenever `SELECT` is edited for an unrelated reason. `Pick` says what the layer promises; `GetPayload` says what one query happens to return.

## Confirmed scoring rule

Extracted from the source app (`server/routes/points.js`, `sumPoints`) and preserved exactly:

- A **nomination** earns the award's point value `P`.
- A **win** earns `P` a second time — so a win is worth **2P total**.
- `team total = Σ movie totals`; `movie total = Σ per-award points`.

🔴 **`P` is not `awards.points`.** That column is a **foreign key into `points.id`** — the source app declared `Awards.hasMany(Points, { sourceKey: 'points', foreignKey: 'id', as: 'pointsData' })` in `server/models/points.js`, and the API exposed the raw FK under the name `points` alongside a resolved `pointsData`. Verified against the restored data: `awards.points` holds values 1–12, all twelve resolve, and none is a point value. "Performance by an Ensemble" stores `1`, which is the Alphabet tier-3 row, worth **5**. A scoring service that summed `award.points` would score it 1 and corrupt every total in the app.

The repository therefore exposes the column as **`Award.pointsId`**, and `P` is `pointRepository.findManyByIds([...pointsIds])`. This is the one place the port deliberately renames a captured API field; the name was actively dangerous.
