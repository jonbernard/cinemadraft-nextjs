# Phase 4 — Auth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace Auth0 with Clerk, and let the 60 existing accounts be *claimed* on first sign-in by verified email — without ever handing one person's leagues to someone else.

**Architecture:** One function, `syncClerkIdentity`, owns every path that can attach a Clerk identity to a `User` row. The webhook calls it and so does the session resolver, because a webhook is asynchronous and a user can reach the dashboard before it arrives. It is idempotent and it fails closed: an unverified address never claims, and a row already claimed by a different identity is never reassigned.

**Tech Stack:** `@clerk/nextjs` 7.7.5 (its `verifyWebhook` wraps svix, so no separate dependency), Next 16 `proxy.ts` (the renamed `middleware` convention), Prisma 7, Vitest.

## Global Constraints

- **D25** — no bulk import. Accounts are claimed on first auth with a **verified** matching email. No Auth0 Management API, no password handling.
- **D26** — passwordless. Email verification code + Google only. Both are verified by construction; the rule is still enforced explicitly so a future connection change cannot silently reopen the hole.
- **D8** — Server Components and Server Actions. `/api` exists only where HTTP is required, which here is the Clerk webhook.
- **D28** — latest stable, verified against the registry.
- **D33** — repository DTOs derive from generated Prisma models. `app/`, `actions/` and `components/` may not reference `generated/prisma` at all. Five `layering` CI checks enforce this and the no-raw-hex rule.
- **D37** — no hex literals outside `theme/`. The Clerk components are themed through tokens.
- **§6** — sign-in and sign-up are the first pages a returning member sees. They use the Phase 3 tokens; no MUI Minimal residue.
- 🔴 The single security-critical rule in this project: **claiming requires a verified email**, and **a claimed row is never reassigned**.

## Data as it actually is (verified 2026-08-14)

- 60 users, **0 claimed** (`clerk_id` null on every row).
- All 60 have `uuid` and `created_at`. Both columns are nullable with **no database default** — Sequelize populated them, so a create path must set them explicitly or produce a row the rest of the app cannot link to.
- `email` is `@unique` and case-sensitive at the database level, but **one** account is stored mixed-case. All 60 are distinct after lower-casing, so case-insensitive matching is unambiguous — and it is required, because Clerk returns lower-cased addresses and an exact match would lock that person out permanently.
- 51 Auth0 email+password users, 9 dormant Firebase-era, 0 Google.

 * Read the auth secrets once, and fail at startup rather than at the first
 * sign-in.
 *
 * A missing CLERK_WEBHOOK_SIGNING_SECRET is the dangerous one: without it the

  return value;

   * Admin repair: move an account to a different Clerk identity (T6).
   *
   * Deliberately unconditional, unlike `claim` — this exists precisely for the
   * cases the safety rules refuse, so an admin can resolve a mismatched email
   * or a logged collision. It is therefore the one function in this file that

  async relink(userId: number, clerkId: string | null): Promise<User> {
    const existing = await db.user.findUnique({ where: { id: userId }, select: SELECT });
    if (!existing) throw new NotFoundError('user', userId);
    return db.user.update({ where: { id: userId }, data: { clerkId }, select: SELECT });
  },

```ts
import { userRepository, type User } from '@/lib/repositories/users';
import { ConflictError, NotFoundError } from '@/lib/errors';

export type ClerkEmail = { address: string; verified: boolean };

export type ClerkIdentity = {
  clerkId: string;
  emails: ClerkEmail[];
  firstName: string | null;
  lastName: string | null;
  image: string | null;
};

export type SyncResult =
  | { status: 'linked' | 'claimed' | 'created'; user: User }
  | { status: 'unverified' | 'collision'; user?: undefined };

/**
 * Attach a Clerk identity to a `User`, or create one. The single path (D25).
 *
 * Both the webhook and the session resolver call this, so the safety rules
 * cannot be true on one path and forgotten on the other. It is idempotent:
 * Clerk redelivers webhooks, and a retry must not be an error.
 *
 * 🔴 Two rules, and they are the reason this function exists rather than the
 * repository being called directly:
 *
 * 1. **Only a verified address may claim.** Linking on an unverified address
 *    would let anyone sign up with another member's email and inherit their
 *    leagues, drafts and history. Clerk's two enabled methods are verified by
 *    construction (D26), so this is belt and braces today — it is enforced
 *    anyway because enabling one more connection must not silently reopen it.
 *
 * 2. **A claimed row is never reassigned.** One person can hold two Clerk
 *    identities (Google once, an email code later). Account linking should
 *    merge them, but this must not depend on dashboard configuration:
 *    overwriting would transfer a member's history to whoever signed in most
 *    recently. A collision is refused and logged for admin repair.
 */
export async function syncClerkIdentity(identity: ClerkIdentity): Promise<SyncResult> {
  const existing = await userRepository.findByClerkId(identity.clerkId);
  if (existing) return { status: 'linked', user: existing };

  const verified = identity.emails.filter((email) => email.verified);
  if (verified.length === 0) {
    // Not an error. Clerk fires user.created before verification completes,
    // then user.updated once it does — claiming simply happens then.
    return { status: 'unverified' };
  }

  for (const email of verified) {
    const legacy = await userRepository.findByEmail(email.address);
    if (!legacy) continue;

    if (legacy.clerkId && legacy.clerkId !== identity.clerkId) {
      console.error('[auth] claim collision', {
        userId: legacy.id,
        heldBy: legacy.clerkId,
        attemptedBy: identity.clerkId,
      });
      return { status: 'collision' };
    }

    try {
      return { status: 'claimed', user: await userRepository.claim(email.address, identity.clerkId) };
    } catch (error) {
      // claim() re-checks under a conditional write, so it can still refuse
      // after the check above — that is the concurrent sign-in case, and the
      // refusal is the correct outcome, not a failure to handle here.
      if (error instanceof ConflictError) {
        console.error('[auth] claim refused', { email: email.address, clerkId: identity.clerkId });
        return { status: 'collision' };
      }
      if (!(error instanceof NotFoundError)) throw error;
    }
  }

  // No legacy row for any verified address: a genuinely new member.
  const primary = verified[0] as ClerkEmail;
  return {
    status: 'created',
    user: await userRepository.createFromClerk({
      clerkId: identity.clerkId,
      email: primary.address,
      firstName: identity.firstName,
      lastName: identity.lastName,
      image: identity.image,
    }),
  };
}
```

```ts
import { currentUser } from '@clerk/nextjs/server';

import { syncClerkIdentity } from '@/lib/services/clerk-identity';
import type { User } from '@/lib/repositories/users';
import { userRepository } from '@/lib/repositories/users';

/**
 * The session holds a Clerk identity but this account cannot be resolved —
 * a collision awaiting admin repair. Distinct from "signed out" because the
 * remedies are opposite: signing in again cannot fix it.
 */
export class AccountLinkError extends Error {
  constructor(readonly clerkId: string) {
    super('this Clerk identity cannot be linked to an account');
    this.name = 'AccountLinkError';
  }
}

/**
 * Resolve the Clerk session to a `User`, syncing if needed.
 *
 * The lazy sync is not redundant with the webhook. A webhook is asynchronous
 * and independently retried: a member can complete sign-in and land on the
 * dashboard before it arrives, and Clerk can drop or delay a delivery
 * entirely. Without this, that member sees an empty account and — worse — a
 * "create your account" path that would fork their history.
 *
 * Both paths call the same function, so the safety rules hold identically on
 * each and there is no second implementation to keep in step.
 */
export async function getCurrentUser(): Promise<User | null> {
  const clerk = await currentUser();
  if (!clerk) return null;

  const known = await userRepository.findByClerkId(clerk.id);
  if (known) return known;

  const result = await syncClerkIdentity({
    clerkId: clerk.id,
    emails: clerk.emailAddresses.map((email) => ({
      address: email.emailAddress,
      verified: email.verification?.status === 'verified',
    })),
    firstName: clerk.firstName,
    lastName: clerk.lastName,
    image: clerk.imageUrl ?? null,
  });

  if (result.status === 'collision') throw new AccountLinkError(clerk.id);
  // 'unverified' is a normal intermediate state, not an error: the member has
  // a session but no confirmed address yet, so there is no account to return.
  return result.user ?? null;
}

export async function requireUser(): Promise<User> {
  const user = await getCurrentUser();
  if (!user) throw new Error('not signed in');
  return user;
}

/**
 * Authorization, not authentication.
 *
 * Throws rather than redirecting: a non-admin reaching an admin action is a
 * bug or an attack, and neither deserves a friendly bounce that hides it.
 */
export async function requireAdmin(): Promise<User> {
  const user = await requireUser();
  if (user.role !== 'admin') throw new Error('admin only');
  return user;
}
```

```ts
import { verifyWebhook } from '@clerk/nextjs/webhooks';

import { syncClerkIdentity } from '@/lib/services/clerk-identity';

/**
 * Clerk tells us an identity changed; we re-run the claim path.
 *
 * `verifyWebhook` checks the svix signature against
 * CLERK_WEBHOOK_SIGNING_SECRET and throws if it does not match. That check is
 * the only thing standing between this endpoint and an attacker posting a
 * chosen email/id pair to claim any account — it must never be bypassed, not
 * even behind a "preview only" flag.
 *
 * Always 200 on a verified-but-unhandled event: a non-2xx makes Clerk retry,
 * and retrying an event we deliberately ignore is noise forever.
 */
export async function POST(request: Request): Promise<Response> {
  let event: Awaited<ReturnType<typeof verifyWebhook>>;
  try {
    event = await verifyWebhook(request);
  } catch {
    // No detail in the response: a precise error tells a prober exactly which
    // part of the signature it got wrong.
    return new Response('invalid signature', { status: 400 });
  }

  if (event.type !== 'user.created' && event.type !== 'user.updated') {
    return Response.json({ ignored: event.type });
  }

  const data = event.data;
  const result = await syncClerkIdentity({
    clerkId: data.id,
    emails: (data.email_addresses ?? []).map((email) => ({
      address: email.email_address,
      verified: email.verification?.status === 'verified',
    })),
    firstName: data.first_name ?? null,
    lastName: data.last_name ?? null,
    image: data.image_url ?? null,
  });

  // A collision is reported as handled: it is a real outcome that a retry
  // cannot improve, and it is already logged for admin repair.
  return Response.json({ status: result.status });
}
```

```ts
'use server';

import { requireAdmin } from '@/lib/auth';
import { userRepository } from '@/lib/repositories/users';

/**
 * Repair path for the two cases the safety rules deliberately refuse: a member
 * whose Clerk email differs from their historical one, and a logged collision.
 *
 * This is the only function in the app that can move an account between
 * identities, which is exactly why it is admin-gated and separate from
 * `claim`. Passing null unlinks, so a mistake here is recoverable.
 */
export async function relinkUser(userId: number, clerkId: string | null) {
  const admin = await requireAdmin();
  console.warn('[auth] admin relink', { by: admin.id, userId, clerkId });
  return userRepository.relink(userId, clerkId);
}
```
